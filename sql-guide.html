Database & SQL Basics

A relational database organizes data into tables (rows + columns). Tables connect through relationships using keys. SQL is the language used to create, query, and manage that data.

Essential SQL Commands

-- Create a table
CREATE TABLE customers (
    customer_id   INT PRIMARY KEY,
    name          VARCHAR(100),
    city          VARCHAR(50),
    created_date  DATE
);
-- Insert, Query, Update, Delete
INSERT INTO customers VALUES (1, 'Alice', 'New York', '2024-01-15');
SELECT name, city FROM customers WHERE city = 'New York';
UPDATE customers SET city = 'Boston' WHERE customer_id = 1;
DELETE FROM customers WHERE customer_id = 1;

Key Types

Primary Key (PK)

Unique row identifier

Cannot be NULL. Each row has exactly one. E.g., customer_id

Foreign Key (FK)

Links two tables

References a PK in another table to create a relationship.

Composite Key

Multi-column PK

Two or more columns together uniquely identify a row.

Super Key

Any unique combo

Any set of columns that uniquely identifies rows — broader than a PK.

DBMS vs RDBMS

Before diving into SQL relationships, it helps to understand the two types of database management systems and how they differ.

DBMS

📁 Data stored in files / non-relational format
🚫 No relationships between data
🔓 Less secure — minimal access control
📊 Best for small, simple datasets
📌 Examples: XML stores, file-based systems
VS

RDBMS

🗂️ Data in tables — rows & columns
🔑 Relationships enforced with keys (PK/FK)
🔒 Data integrity via ACID properties
🏗️ Handles large, complex datasets
📌 Examples: MySQL, PostgreSQL, Oracle, SQL Server
ACID = Atomicity (all or nothing), Consistency (rules always apply), Isolation (transactions don't interfere), Durability (committed data survives crashes). RDBMS guarantees all four; plain DBMS does not.

Many-to-Many — Junction Table Example

CREATE TABLE students (student_id INT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE courses  (course_id  INT PRIMARY KEY, name VARCHAR(50));

-- Junction table bridges the many-to-many
CREATE TABLE student_courses (
    student_id INT REFERENCES students(student_id),
    course_id  INT REFERENCES courses(course_id),
    PRIMARY KEY (student_id, course_id)  -- composite PK
);

Database Normalization

Normalization organizes tables to eliminate redundancy and prevent data anomalies. Applied progressively through Normal Forms.

3 Anomalies Prevented: Insertion (can't add data without unrelated data) · Deletion (removing a row loses other important data) · Update (changing one copy doesn't update duplicates).
Normal FormRuleWhat it Fixes
1NFAtomic values, no repeating column groups, must have a PKArrays in cells, duplicate column sets (child1, child2, child3)
2NFNo partial dependency on a composite PKNon-key column depends on only part of the composite PK
3NFNo transitive dependency — non-key can't depend on non-keydept_name depending on dept_num (not the actual PK)
BCNFEvery determinant must be a candidate keyEdge cases 3NF misses
4NFNo multi-valued independent dependenciesEmployee skills and languages in one table
5NFDecomposition must be losslessJoining sub-tables creates phantom rows

3NF Example — Before & After

-- PROBLEM: dept_name depends on dept_num, not on emp_num (the PK)
-- emp_num | name  | dept_num | dept_name  ← redundant, causes update anomaly

-- SOLUTION: Split into 3 tables
CREATE TABLE employee   (emp_num INT PK, fname, lname);
CREATE TABLE department (dept_num VARCHAR PK, dept_name);
CREATE TABLE emp_dept   (emp_num INT FK, dept_num VARCHAR FK);

OLAP vs OLTP

The two dominant processing paradigms — OLTP handles live transactions, OLAP handles analytical queries. Most organizations run both in parallel.

OLTP — Online Transaction Processing

Real-time execution of many short transactions. Powers ATMs, banking, ticket booking, shopping carts.

✓ Pros: Fast read/write, supports ACID, high availability, up-to-date data.

✗ Cons: Limited analytics, high maintenance, susceptible to hardware failures.

OLAP — Online Analytical Processing

Complex read-heavy queries over large historical datasets. Powers BI tools, Spotify recommendations, Netflix suggestions.

✓ Pros: Multidimensional analysis, trend detection, handles TB–PB data.

✗ Cons: Complex modeling, expensive, updated in batches not real-time.

UpdatesPeriodic batchesFrequent, real-time

Star Schema vs Snowflake Schema

Data warehouse schemas use a central Fact Table (measurable events) surrounded by Dimension Tables (context: who, what, when, where).

Star Schema — Denormalized

DIM_Customer
name, city, region, country
DIM_Date
day, month, quarter, year
DIM_Product
name, category, brand
↘ direct FK links ↙
★ FACT_Sales
sale_id · customer_id (FK) · product_id (FK) · date_id (FK)
amount · quantity

Snowflake Schema — Normalized Dimensions

Dimensions split into sub-tables. DIM_Customer references DIM_City → DIM_Region. Less redundancy, more JOINs.

CREATE TABLE dim_region   (region_id PK, region_name, country);
CREATE TABLE dim_city     (city_id PK, city_name, region_id FK);
CREATE TABLE dim_customer (customer_id PK, name, city_id FK);

Slowly Changing Dimensions (SCD)

Dimension data changes over time. SCDs define how to handle those changes while preserving historical accuracy. Example: Customer Amir moves Delhi → Mumbai.

0
Fixed

Immutable. Never changes. E.g. date_of_birth.

1
Overwrite

Old value replaced. No history kept.

2
New Row

New record per change. Full history via surrogate key + dates.

3
New Column

Adds previous_city column. One prior value only.

4
History Table

Current in main table; history in separate table.

6
Hybrid

Combines types 1+2+3. Most flexible.

Type 2 — Most Common in Practice

-- When Amir moves city — expire old row, insert new row
UPDATE dim_customer
SET end_date = '2024-06-01', is_current = FALSE
WHERE customer_id = 101 AND is_current = TRUE;

INSERT INTO dim_customer VALUES (2, 101, 'Amir', 'Mumbai', '2024-06-01', NULL, TRUE);

-- surr | cust | city   | start      | end        | current
-- 1    | 101  | Delhi  | 2020-01-01 | 2024-06-01 | FALSE  ← history
-- 2    | 101  | Mumbai | 2024-06-01 | NULL       | TRUE   ← current

Apache Iceberg: Spark SQL vs DataFrames

Apache Iceberg is a modern open table format for huge analytic datasets. In PySpark you can interact with Iceberg tables using either Spark SQL (familiar, readable) or the DataFrame API (flexible, programmatic).

Spark SQL

SQL Syntax

✓ Familiar for SQL users · Readable for complex ops
✗ Less flexible · No compile-time type safety

DataFrames

Programmatic API

✓ Flexible · Type safe · Great for iteration
✗ More verbose · Steeper learning curve

Session Setup (same for both)

from pyspark.sql import SparkSession

spark = SparkSession.builder \
  .appName("IcebergDemo") \
  .config('spark.jars.packages', 'org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.5.2') \
  .config("spark.sql.extensions", "org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions") \
  .config("spark.sql.catalog.local", "org.apache.iceberg.spark.SparkCatalog") \
  .config("spark.sql.catalog.local.type", "hadoop") \
  .getOrCreate()

Create · Append · Query · Transform · Delete

### Spark SQL ###
spark.sql("""
  CREATE TABLE local.sql.data_points (id INT, name STRING, value INT) USING iceberg
""")
spark.sql("""INSERT INTO local.sql.data_points VALUES (1,'metric_1',5),(2,'metric_2',10)""")

### DataFrame API ###
from pyspark.sql.types import StructType, StructField, StringType, IntegerType
schema = StructType([StructField("id", IntegerType()), StructField("name", StringType()), StructField("value", IntegerType())])
data = [(1,'metric_1',5), (2,'metric_2',10)]
df = spark.createDataFrame(data, schema)
df.writeTo("local.df.data_points").using("iceberg").create()
### Spark SQL ###
spark.sql("""INSERT INTO local.sql.data_points VALUES (6,'metric_2',5),(7,'metric_1',10)""")

### DataFrame API ###
new_data = [(6,'metric_2',5), (7,'metric_1',10)]
append_df = spark.createDataFrame(new_data, schema)
append_df.writeTo("local.df.data_points").using("iceberg").append()
### Spark SQL ###
spark.sql("SELECT * FROM local.sql.data_points WHERE name='metric_1' ORDER BY id").show()

### DataFrame API ###
import pyspark.sql.functions as F
spark.read.format("iceberg").table("local.df.data_points") \
  .where(F.col("name").eqNullSafe("metric_1")) \
  .orderBy('id').show()
### Spark SQL — simple ALTER ###
spark.sql("ALTER TABLE local.sql.data_points ADD COLUMNS (source STRING)")

### DataFrame API — mergeSchema ###
from pyspark.sql.functions import lit
evolved_df = append_df.withColumn("source", lit(None).cast(StringType()))
evolved_df.writeTo("local.df.data_points") \
  .option("mergeSchema", "true").using("iceberg").append()
### Spark SQL ###
spark.sql("DELETE FROM local.sql.data_points WHERE source = 'source_1'")

### DataFrame API — filter to keep, then replace ###
keep_df = transformed_df.where(F.col("source") != "source_1")
keep_df.writeTo("local.df.data_points") \
  .option("mergeSchema","true").using("iceberg").replace()
Key difference on delete: Spark SQL uses a direct DELETE statement. The DataFrame API has no delete primitive — you filter the rows you want to keep and call .replace() to overwrite the table.
